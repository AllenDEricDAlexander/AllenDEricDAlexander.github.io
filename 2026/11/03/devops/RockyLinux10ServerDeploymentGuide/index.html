Rocky Linux 10 服务器初始化、系统管理与常用服务部署实战

Rocky Linux 10 服务器初始化、系统管理与常用服务部署实战

新装一台 Linux 服务器，真正需要完成的不只是“换源、装 vim、关防火墙”。当机器要加入虚拟化环境、承担数据库或容器工作负载，网络、存储、时钟、访问控制和软件版本必须作为一套配置来考虑。本文将日常 Rocky Linux 运维笔记与 Rocky Linux 基础操作经验合并，整理出一条从空白系统到可交付服务器的实施路线，并补充 PostgreSQL、Docker、Redis、MySQL、Nacos、Kafka、GitLab 等常见组件的部署参考。

本文以 Rocky Linux 10 为主。被引用的博客侧重 Rocky Linux 8，一些命令在 Rocky Linux 9 尚能兼容、到 10 已完全失效，因此文中会特别标记迁移差异。所有 IP、磁盘设备和域名仅用于演示，执行前必须替换为真实环境参数。

Rocky Linux 与 RHEL 同一大版本保持高度兼容，但它并不是“CentOS 8 的稳定版本”。尤其在 Rocky 10 中，网络配置发生了关键变化：

Rocky Linux 10 不应再沿用旧教程中的 vim /etc/sysconfig/network-scripts/ifcfg-eth0、systemctl restart network 或 dnf module enable redis:6。这不是命令写法不同，而是软件栈的支持边界发生了变化。详见 Rocky Linux 10 发布说明 和 RHEL 10 网络迁移说明。

二、识别系统信息与软件仓库

2.1 查看系统、内核和硬件

几个主要信息要区分清楚：/etc/os-release 显示发行版本，uname -r 是运行中的内核版本，lsblk 反映块设备与挂载情况。服务器刚交付时，最好先记录这些状态，方便故障回滚与资产盘点。

2.2 DNF、YUM 与软件源

Rocky Linux 默认使用 dnf 管理 RPM 软件包。yum 在现代 RHEL 系发行版上通常作为兼容入口，建议新脚本直接使用 dnf。

基础仓库中，BaseOS 提供核心操作系统组件，AppStream 提供应用程序包，Extras 用于补充软件；CRB 用于补齐部分开发依赖，启用 EPEL 时通常也要启用它。

2.3 更换国内镜像（按需）

海外机房可直接保留官方 mirrorlist；仅在国内访问官方源存在明显延迟时考虑替换。先备份，再替换，最后验证仓库信息。Rocky Linux 9/10 的默认文件通常是小写的 rocky.repo、rocky-extras.repo，而 Rocky 8 教程里经常是 Rocky-BaseOS.repo 等文件。

如果使用阿里云，将上面镜像地址按其实际目录替换为 https://mirrors.aliyun.com/rockylinux；各镜像站目录名不一定一致，不能只替换域名。遇到元数据或 GPG 校验失败，应恢复备份并检查仓库状态，不建议关闭 gpgcheck 来绕过问题。

2.4 启用 CRB 与 EPEL

EPEL 是 Extra Packages for Enterprise Linux，用于提供企业 Linux 基础仓库没有的扩展软件。它不是 Rocky 官方核心仓库，涉及生产环境时应纳入软件源治理和升级测试。

如果确实需要替换 EPEL 镜像，先检查当前 epel.repo 的 metalink、baseurl，再按镜像站提供的 EL10 指南修改，避免套用 EL8 的 epel-modular 旧配置。

2.5 更新系统与保留内核

dnf upgrade 与 dnf update 在常见维护流程中不必连续执行。dnf autoremove 会删除被判定为不再需要的依赖，应先预览删除清单，不要直接写进无人值守脚本。

早期教程建议在 /etc/yum.conf 中永久添加 exclude=kernel*。这种做法会漏掉内核安全修复，不适合作为默认策略。若只想在某次维护窗口临时排除内核，可以使用：

六、SELinux、Firewalld 与主机安全

6.1 SELinux 的正确处理方式

网络上常见的 Rocky 初始化脚本会直接将 SELINUX=disabled。这能够减少一些服务启动时的权限问题，但也会失去一层重要的强制访问控制。生产服务器建议优先保持 Enforcing，只有排障时暂时转入 Permissive。

若实验环境明确要求将宽容模式设为持久状态，可编辑 /etc/selinux/config 中的 SELINUX=permissive，随后重启验证。不要将“禁用 SELinux”视为所有 Web、数据库或容器问题的通用修复方案，优先检查上下文标签、布尔值与服务策略。

十九、Jenkins、Nexus 与开发基础设施

19.1 Jenkins 安装

旧笔记以 Java 11 运行 Jenkins。到 2026 年，新版本 Jenkins 已提升运行时最低要求，当前支持的运行时主要是 Java 21 / Java 25。不要按旧文档下载过时的 Java 11 二进制包。

生产 Jenkins 建议部署在专门管理网络，启用 HTTPS、统一身份认证、角色权限和 Controller/Agent 分离，避免在 Jenkins Controller 上直接运行不可信构建任务。最新运行环境要求请以 Jenkins Java 支持策略 为准。

19.2 Nexus Repository

Nexus 常用于统一管理 Maven、npm、Docker 等制品。其安装包、Java 兼容性、系统用户及磁盘目录与所选择的 Nexus Repository 版本有关，不能仅凭旧安装命令确定。

推荐部署思路：

  1. 从 Sonatype 官方网站 获取支持的版本与安装说明。
  2. 为 Nexus 建立非 root 系统用户，数据存入独立挂载卷。
  3. 通过 systemd 管理服务，使用 Nginx 反向代理与 HTTPS 提供入口。
  4. 按 Maven、npm、Docker 分别配置 Hosted、Proxy、Group 仓库，并建立备份与存储容量监控。

不建议将 Nexus 的系统端口、Docker Registry 入口、Maven 私服路径全部混用为同一个“通用端口”，实际访问路径应根据客户端协议分开验证。
