分布式一致性与共识协议：从 CAP、Paxos、Raft 到 PBFT、PoW 与 ZAB

分布式系统将数据和计算分散到多个节点后，真正困难的并不是让节点之间发送消息，而是在网络分区、节点宕机、并发写入，甚至恶意节点参与的条件下，让系统对外呈现可理解、可恢复的行为。本文围绕这一问题，将 CAP、ACID、BASE 与二阶段提交等事务机制，与 Paxos、Multi-Paxos、Raft、ZAB、PBFT、PoW 等共识协议联系起来，同时讨论一致哈希、Gossip、反熵和 Quorum NWR 如何解决数据分布、传播与副本读取问题。重点放在协议成立的前提、关键消息流、故障恢复、工程代价及选型边界。

分布式系统究竟需要在哪些事情上达成一致

假设我们实现了一个三节点 KV 存储，最初各节点的 X 都是 1。客户端向节点 A 写入 SET X = 2，A 立即返回成功，但消息尚未到达 B、C。另一个客户端随后从 B 读到 X = 1。从单机数据库的使用经验来看，这很反直觉；但在分布式系统中，这正是最普通的故障与延迟场景。

如果要求客户端在写入成功后，无论访问哪个可读节点都能看到新值，就必须设计额外的同步、协调或读协议。若允许节点暂时提供旧值，则需要回答另一组问题：什么时候收敛？冲突写入如何解决？丢掉的消息如何补发？

这些问题表面上都叫“一致性”，但实际对应不同的系统职责。

需要解决的问题 典型机制 真正保证的事情
多个参与者是否一起提交业务操作 2PC、XA、TCC 一个分布式业务操作的提交或取消协调
多节点对某个值或操作序列达成决定 Paxos、Raft、ZAB 共识安全性及复制状态机的一致演进
有节点蓄意发送矛盾消息时如何决定 PBFT 等 BFT 协议 在指定恶意节点上限内达成可信决定
无准入中心的网络如何竞争记账权 PoW 通过算力成本与累积工作量形成概率性共识
数据应路由到哪个分片或集群 一致哈希 数据放置与扩缩容时尽量少迁移
副本之间怎样传播和修复数据 Gossip、反熵 在满足传播与冲突处理前提下逐步收敛
读几个副本、写几个副本才算完成 Quorum NWR 通过读写集合交集调节延迟、可用性和可见性

共识、事务、数据路由和数据同步不是互相替代的算法。 一个真正可扩展的存储系统很可能同时使用它们：一致哈希负责选择分片，Raft 负责分片内复制，Gossip 负责传播节点状态，事务协调层负责跨分片操作。

故障模型决定了协议能承诺什么

讨论某个算法能容忍多少节点之前，必须先明确节点究竟会怎样出错。

崩溃故障（Crash Fault） 主要指进程或机器停止工作。通信还可能超时、丢失、重复、乱序，但节点不会故意违反协议、伪造其他节点身份，或给不同节点发送自相矛盾的“承诺”。Paxos、Raft、ZAB 通常按照非拜占庭的崩溃故障模型设计，属于 CFT（Crash Fault Tolerance）范畴。

拜占庭故障（Byzantine Fault） 则允许故障节点任意行动：谎报数据、对不同节点发送不同结果、故意拒绝转发消息，乃至尝试欺骗协议参与者。PBFT 面向这种问题。PoW 也用于抵御开放网络中的恶意参与者，但其安全模型以算力资源和概率性链选择为基础，不能直接套用 PBFT 的节点人数公式。

另外，还需要区分协议的两项性质：

  • 安全性（Safety）：不应该发生的事情永远不发生。例如同一个日志位置不会提交两个互相冲突的值，已提交的记录不会因选主而丢失。
  • 活性（Liveness）：应该完成的事情最终能够完成。例如网络恢复、足够多节点可用后，集群能再次选主并处理请求。

一个系统即使暂时无法写入，也可以保持安全；为了可用而让两个网络分区各自提交互相冲突的决定，则可能直接破坏安全性。多数共识算法优先保住 Safety，再依靠网络恢复、选举超时和故障转移恢复 Liveness。

多数派为什么如此重要

对 N 个投票节点，严格多数派的大小为：

[
Q=\left\lfloor\frac{N}{2}\right\rfloor+1
]

任意两个这样的多数派一定至少共享一个成员。以五节点集群为例，任何两个三节点集合都不可能完全不相交。这项简单的集合性质是 Paxos、Raft、ZAB 等协议中防止冲突决定的重要基础。

假定故障不会作恶，采用多数派的系统通常可以在 N=2f+1 时容忍 f 个节点崩溃，并维持继续提交的能力。三节点容忍一个，五节点容忍两个；它并不意味着任何五节点系统都具有相同的存储持久性、业务可用性或读一致性。

CAP：发生网络分区时，系统准备保留什么

CAP 定理抽象出一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）之间的限制。它不是给某个数据库贴上“CP”或“AP”标签就结束的分类题，而是要求设计者回答：当持有同一份数据的节点无法彼此通信时，请求应当等待、失败，还是继续使用可能滞后的状态？

C、A、P 的精确定义

CAP 中的 C 通常按照**线性一致性（Linearizability，又称原子一致性）**理解：每个操作都好像在发起和返回之间的某个瞬间原子生效，而且全局顺序尊重真实时间的先后关系。一次写入已经成功返回后，后续读操作不能再从系统中读到该写入之前的版本，除非发生了更新的写入。

A 是定理语境下的可用性：每个送到非故障节点的请求最终都能够得到协议要求的响应。它与运维报表里的 99.99% SLA、平均延迟或“首页还能打开”不是同一个定义。

P 表示即使网络在不同节点间丢弃或无限期延迟消息，系统也需要考虑如何表现。它不是可随手关闭的一项技术功能；只要节点可能被网络分开，就必须接受这种故障模型。

flowchart LR
    C[客户端]
    subgraph P1[多数派分区]
      A[副本 A: X=2]
      Q[副本 C: X=2]
    end
    subgraph P2[少数派分区]
      B[副本 B: X=1]
    end
    C -->|已确认写入 X=2| A
    A --- Q
    A -.->|网络分区阻断同步| B
    C -->|随后读取 X| B
    B --> D{如何响应?}
    D -->|等待或拒绝| CP[保留一致性]
    D -->|返回旧值 1| AP[保留可用性]

当分区存在时，如果 B 无法确认 A 的最新写入情况，B 既不能保证返回新值，又不能一边坚持线性一致性一边保证每个请求都成功完成。CAP 所陈述的冲突就在这里。

常见说法“CAP 三选二”容易误导。不是所有时刻都只能在 C 和 A 之间选择一个，而是在网络分区期间，不能同时满足定理所要求的 C 和 A。 网络正常时，一套协议可以同时提供很好的读取一致性和可用性，但依然有延迟、吞吐量、复制成本方面的取舍。

CP 与 AP 不是整个系统永久不变的身份

CP 倾向在分区期间限制无法确认最新状态的操作，例如 Raft 集群失去多数派后停止提交写入。这样牺牲了一部分请求的可用性，避免两个分区各自确认矛盾的数据。

AP 倾向让彼此隔离的节点继续处理请求，之后再同步和调解冲突。读到旧值、出现并发版本甚至后续合并，是需要明确接受的语义，而不是免费获得高可用。

“CA 系统”也不宜直接对应单机 MySQL 或某个产品名称。CAP 讨论的是会发生网络分区的分布式系统；在没有分区故障的运行区间，可以同时有 C 和 A，但不能因此声称分区不再需要处理。

同一产品可以对不同数据采用不同策略

一个时序数据库可以分为两层：

flowchart TB
  U[客户端]
  M[元数据服务 META<br/>库、保留策略、分片分配]
  D[数据服务 DATA<br/>时序记录、分片、副本]
  U --> M
  U --> D
  M -->|提供路由和配置| D
  M --> MC[多数派共识<br/>优先一致性]
  D --> DA[多副本异步复制<br/>优先写入与扩展]

META 存储库名、分片位置、保留策略等控制平面数据。若一个节点告诉写入客户端“数据库存在”，另一个节点却认为“数据库不存在”，就可能造成路由错误和业务失败。因此元数据适合采用多数派共识，对不确定状态采取更保守的策略。

DATA 保存高吞吐时序记录，业务可能更看重写入持续性、批量查询和横向扩展。此时可以允许数据副本短时间不一致，再用副本传播与反熵修复。代价是读数据时必须处理滞后、缺失、重复和冲突。

这是一种基于业务语义的架构划分，不意味着所有 InfluxDB 版本或所有时序数据库都采用相同实现。也不能由“用了 Raft”推出“整个数据库不能水平扩展”：Raft 只限定单个共识组的写入协调方式，多个独立共识组可以分片并行工作。

ACID 与 BASE：事务约束和可用性策略

CAP 的 C 经常与 ACID 的 C 混为一谈，甚至把 ACID 与 BASE 说成一组非此即彼的技术。这样理解很容易让系统选型出现偏差。

ACID 约束的是事务

ACID 描述数据库事务的四项关键性质：

特性 含义 工程关注点
Atomicity，原子性 事务包含的操作整体提交，或整体不产生已提交效果 日志恢复、回滚、跨资源提交协议
Consistency，一致性 事务使数据从一个满足约束的状态转到另一个满足约束的状态 唯一约束、外键、金额守恒、业务不变量
Isolation，隔离性 并发事务的相互影响符合指定隔离级别 锁、MVCC、并发异常和隔离级别
Durability，持久性 成功提交后的结果在规定故障模型下不会丢失 WAL、刷盘、备份和故障恢复

这里的 ACID Consistency 指事务前后保持数据库约束，不是 CAP 所要求的所有读写操作具有线性化顺序。一个系统可以在单个节点上提供 ACID 事务，但通过异步副本复制产生跨节点的旧读；也可以使用一致性共识保证日志顺序，却仍然需要单独实现事务隔离。

BASE 允许副本在一段时间内暂时不同

BASE 通常展开为 Basically Available（基本可用）、Soft State（软状态）和 Eventually Consistent（最终一致性）。其思想是：遇到故障或负载尖峰时，优先保留核心服务，并允许数据经过一段时间逐步收敛。

“最终一致”包含一个常被省略的前提：停止产生新的冲突更新、网络能够恢复传播、修复机制持续推进，而且冲突有明确的收敛规则。 它不是“等一等自然就一致了”，更不是系统能够容忍数据永久丢失。

业务级的基本可用也不同于 CAP 定理对 A 的严格定义。例如抢票服务排队返回“正在处理”，以排队降低核心写路径的压力，属于合理的高可用设计，却不等于对应事务已经完成。

应对流量和故障的典型手段包括：

  • 削峰：错峰开放、写入队列、异步批处理，将尖峰转化为可控吞吐。
  • 延迟响应：向客户端返回任务编号和处理中状态，后续查询最终结果。
  • 功能降级：舍弃非核心推荐、高清图片等能力，维持关键路径。
  • 过载保护：限流、熔断、队列上限、超时预算、隔离故障依赖。

BASE 不是放弃数据正确性，而是把“哪些数据允许短暂落后、最多落后多久、如何发现和修复”变成明确的业务约定。元数据、支付流水、实时监控曲线和社交在线状态，通常不应使用同一套一致性承诺。

分布式事务：2PC、XA 与 TCC 怎样协同多个资源

当一个操作需要同时更新几个独立的数据库或服务，单节点事务无法直接把它们包成一个原子提交单元。典型例子是业务侧的资金转移：从账户 A 扣减 100 元，同时向账户 B 增加 100 元。如果两个资源的提交彼此独立，系统宕机时就可能只完成一半。

二阶段提交：所有参与者准备好之后再作决定

二阶段提交（Two-Phase Commit，2PC）由协调者（Coordinator）组织多个参与者（Participant），分为准备阶段与决定阶段。

sequenceDiagram
    participant C as 事务协调者
    participant A as 参与者 A
    participant B as 参与者 B
    C->>A: PREPARE(txId)
    C->>B: PREPARE(txId)
    A->>A: 执行并持久化准备状态、保留资源
    B->>B: 执行并持久化准备状态、保留资源
    A-->>C: VOTE YES
    B-->>C: VOTE YES
    C->>C: 持久化 COMMIT 决定
    C->>A: COMMIT(txId)
    C->>B: COMMIT(txId)
    A-->>C: ACK
    B-->>C: ACK

如果准备阶段有参与者投 NO 或无法准备，协调者应根据协议决定中止并通知参与者回滚。一个参与者一旦投出 YES，必须能够在进程崩溃并重启后继续履行最终决定。因此准备记录、协调者决定等关键信息需要持久化，而不是仅存于内存。

2PC 的成本不仅是多一次网络交互。参与者准备成功后往往持有锁或资源预留；如果协调者在公布结果前故障，处于 PREPARED 状态的参与者可能长期无法独立判断应该提交还是回滚，这就是经典的阻塞问题。

2PC 不等于 Paxos 的两阶段。 两者都出现“第一阶段、第二阶段”的消息结构，但 2PC 协调一个分布式事务的原子决定；Paxos 在可能有不同提议者和故障的情况下选择一个安全的值。不能因为它们都分两阶段，就认定其容错性质一样。

XA：数据库资源参与的分布式提交接口

XA 是 X/Open DTP 体系中用于分布式事务管理器与资源管理器协作的接口规范。支持 XA 的数据库能够参与准备、提交、回滚等过程；MySQL 的 XA 事务就是常见实例。

XA 的优势是事务协调逻辑可以相对独立于具体业务操作，适合需要跨事务资源保持原子提交语义的场景。但它对资源管理器能力、日志恢复、连接管理和长时间持锁都有要求。遇到高并发或跨机房长延迟时，应评估锁等待和故障恢复的代价。

TCC：把资源预留、确认和取消显式放到业务层

TCC 代表 Try、Confirm、Cancel。它不要求每个业务参与者长期持有同一个数据库事务，而是让业务定义三个能够独立重试的动作。

flowchart TD
  S[开始全局事务] --> T[对各参与者执行 Try<br/>校验条件并预留资源]
  T --> R{全部 Try 成功?}
  R -->|是| C[执行 Confirm<br/>将预留转换为正式完成]
  R -->|否| X[执行 Cancel<br/>释放已预留资源]
  C --> E[记录全局成功]
  X --> F[记录取消结果]

例如库存扣减可以按业务状态实现：Try 将可售数量中的指定额度转为预留数量，Confirm 将预留量实际消耗，Cancel 则释放预留量。这里的状态变迁必须由业务自己编码，不能简单地把三次普通 SQL 更新包装为“分布式事务”就认为安全。

TCC 的关键实现要求通常包括：

  • 幂等：同一个 txId 的 Confirm/Cancel 多次执行应保持一次执行的效果。
  • 空回滚处理：Try 尚未成功或消息尚未到达时，Cancel 先到不能误修改不属于该事务的资源。
  • 防悬挂：Cancel 已成功后，迟到的 Try 不能重新预留资源。
  • 状态持久化：参与者需要能根据事务号识别 TRYING、CONFIRMED、CANCELLED 等状态，恢复后继续处理。
  • 重试和对账：超时意味着结果未知，不等于远端一定没执行；需要能查询状态、重试补偿与发现漏单。

TCC 对锁粒度和资源管理更灵活，但增加业务代码复杂度。如果事务天然由数据库管理且吞吐可接受，优先利用成熟事务能力通常更稳妥；跨服务且适合业务预留/补偿的操作，再考虑 TCC。

早期的三阶段提交（3PC）通过额外阶段和超时机制试图减轻阻塞，但不能简单推导出“引入超时就能在任意网络分区下安全提交”。它也并非今天分布式事务的通用替代方案。

拜占庭将军问题：为什么多数表决还不够

在没有恶意行为的世界里，“收到过半节点的确认”是一个很强的基础。但如果有参与者可以向不同人撒不同的谎，同一个表决过程就不再安全。

假设只有三位将军，其中齐主张撤退、燕主张进攻，楚是叛徒。楚向齐说“撤退”，却向燕说“进攻”。两位诚实将军分别计算自己看到的多数意见：齐得到“撤退 2、进攻 1”，燕却得到“撤退 1、进攻 2”。即使每个人严格按照多数规则行事，最终也会做出不同决定。

这个故事抽象出拜占庭共识的本质问题：正常节点不仅要决定选哪个值，还要在恶意节点发送不一致消息时，仍然做出相同决定。

无签名口信模型与 3f+1 门槛

在经典拜占庭将军问题的口信模型中，消息的来源可以识别，但不能依靠可转发、不可伪造的数字签名来证明原始内容。在同步通信、消息可按约定轮次送达等前提下，若最多有 f 个叛徒，要解决对应的拜占庭一致性问题，需要至少：

[
N\geq 3f+1
]

这个结论不是简单地“正常节点人数超过异常节点两倍”就能解释；关键是不同诚实节点得到的视图可能不同，算法必须确保递归转发后的决策仍一致。

对于一名叛徒，需要至少四位将军。典型的口信消息方案通过多轮消息传递，让接收者收集其他将军对指挥官命令的转述，再用统一规则做决定。若容忍 f 个叛徒，需要执行 f+1 层的消息传播与决策过程。

在这种递归构造下，消息成本会随容忍的叛徒数量急剧增加，通常可用与 O(N^{f+1}) 同量级的上界描述。它适合说明问题为什么困难，却不适合直接作为普通生产集群的复制协议。

带签名的消息改善了什么

若所有参与者身份已知，诚实节点的签名不可伪造，消息被修改后能够检测，而且其他节点能够验证并转发带签名的原始消息，那么恶意节点就难以谎称“另一个诚实节点说过某句话”。

此时可以设计签名消息算法：转发消息时携带完整签名链，所有正常节点按相同的取值规则处理收集到的有效消息。它与无签名口信模型的容错限制不同，在原始算法的特定通信与认证假设下可以处理更强的叛徒比例。

但签名只证明谁签发了这条消息，并不证明消息内容为真；恶意节点完全可能用自己的合法密钥签署两条矛盾的消息。如何在出现这种分叉时保持安全，仍需要协议级处理。数字签名也不能消除网络分区、超时、密钥泄露、成员身份管理或活性问题。

这就解释了为什么在工程实践中，还需要 PBFT 等完整的拜占庭容错复制协议，而不是给普通的 Raft RPC 加上一层签名就宣布获得 BFT 能力。

Paxos：让多个节点对一个值作出不可推翻的决定

如果排除了恶意节点，问题可以收窄为：不同客户端可能并发提议不同的值，部分节点随时会宕机，消息可能被延迟或重传，怎样保证系统最终最多只选定一个值？

Basic Paxos 对此给出了非常经典的答案。

Basic Paxos 的三种角色和提案

  • Proposer（提议者）：提出某个提案，协调投票。
  • Acceptor（接受者）：记录承诺和已接受的提案，参与多数派决定。
  • Learner（学习者）：得知已经被选定的值，用于更新本地状态。

角色是协议职责，不一定对应三台不同机器。同一个服务节点可以同时是 Proposer、Acceptor 和 Learner。

一个提案写作 (n, v)，其中 n 是全局可比较且唯一的提案编号，v 是希望被选定的值。对同一个 Paxos 实例，接受者需要保留至少两类持久化状态：

接受（Accepted）不等于选定（Chosen）。 某个 Acceptor 接受一个值，只表示本节点记录了它；同一个提案被一个多数派接受，才意味着该值已经被选定。学习者也不应只因为收到一条接受通知就立即当作全局共识。

Prepare / Promise：先确认自己是否可以安全提出值

第一阶段是准备与承诺（Prepare / Promise）。Proposer 选择一个比自己此前使用的编号更大的 n，向 Acceptor 发送 Prepare(n)。

Acceptor 若尚未承诺比 n 更大的编号，就可以更新承诺并返回 Promise，同时告诉提议者：自己曾经接受过的最高编号提案是什么。之后它不能再接受编号小于自己承诺的提案。

当 Proposer 从多数派收到 Promise 后，不一定能直接使用客户端新提交的值。它必须检查所有成功响应：

  • 如果这些 Acceptor 从未接受过任何提案，可以使用自己要提议的新值；
  • 如果已有接受记录，必须选取其中被接受编号最高的提案所携带的值，作为本轮要提议的值。

这项看似不直观的规则正是 Paxos 保住已选定值的关键。它使更高编号的提议者能够接续先前的决定，而不是以“我的编号更大”为由覆盖它。

Accept / Accepted：在多数派中选定同一个值

第二阶段是接受（Accept）。Proposer 发送 Accept(n, v)，Acceptor 如果没有承诺过更大的编号，就接受并持久化该提案，再返回确认。

    participant P as Proposer
    participant A as Acceptor A
    participant B as Acceptor B
    participant C as Acceptor C
    P->>A: Prepare(n)
    P->>B: Prepare(n)
    P->>C: Prepare(n)
    A-->>P: Promise(已接受的最高提案)
    B-->>P: Promise(已接受的最高提案)
    Note over P: 收到多数派承诺<br/>确定允许提议的值 v
    P->>A: Accept(n, v)
    P->>B: Accept(n, v)
    A-->>P: Accepted(n, v)
    B-->>P: Accepted(n, v)
    Note over P: 同一提案得到多数派接受<br/>值 v 已选定

例如两个客户端分别想把只读变量 X 定为 3 和 7。并发 Prepare 可能互相抢占；假设编号为 5 的提议者成功取得多数派承诺，且此前无人接受过别的值，那么它可以提议 (5, 7)。当这个提案被多数派接受，X=7 被选定。此后，即使另一个 Proposer 使用编号 10 重新协调，也必须通过 Promise 找到可能已被选定的 7，并继续提议它。

为什么两个多数派的交集能够保住安全性

假设值 v 已经被一个多数派接受。任何后续取得多数派 Promise 的 Proposer，都至少能联系到这个多数派中的一个节点；更高编号的提案则必须遵守“沿用最高已接受编号对应的值”的规则。结合协议不变量，可以保证后续被选定的值不会与 v 冲突。

这里需要两件事同时成立：多数派交集和正确的提案继承规则。只拿到过半赞成票，却任意改写值，不是 Paxos。

Paxos 主要保证 Safety。在异步网络中，多个 Proposer 可能不断使用更大的编号彼此抢占，迟迟无法选定值。实际系统因此通常会引入稳定领导者、退避机制以及适当的超时与失败检测，以改善活性。

Multi-Paxos：从“一个值”演变成“一系列操作”

单个 Basic Paxos 实例只能确定一个值。数据库和配置系统却需要不断处理写入操作，如果每一条记录都从 Prepare 重新开始，就会产生大量消息往返。

Multi-Paxos 的常见实现思路是让多个 Paxos 实例分别决定日志中的不同位置，并尽量由一个稳定的 Leader 负责提议：

  1. 通过准备阶段建立当前领导者的有效提案编号，学习并继承已有接受记录。
  2. 在领导权稳定且协议条件满足时，后续日志位置通常可以省略逐条重新执行 Prepare 的步骤。
  3. Leader 为新日志位置提议值，通过接受阶段获得多数派确认。
  4. 领导者变更时，新领导者恢复必要的历史状态，填补或处理未决位置，继续安全提议。

这样稳定状态下每个操作的协商延迟可以少一个往返阶段，但领导权争夺、历史恢复、成员变更、日志空洞和提交可见性都需要额外设计。

“Multi-Paxos”常用来泛指这种多实例、基于 Paxos 思想的协议族，并不是每个系统都有完全相同的消息、选举和日志实现。Raft 与 Multi-Paxos 可以在复制状态机结果上实现相近保证，但 Raft 是具有自身明确规则的协议，不应把两者直接当成同一份算法。

Chubby：稳定主节点与租约是工程化的关键

Google Chubby 是 Paxos 思想在分布式协调服务中的经典实践。其实现围绕主节点组织请求，通过主节点租约（Lease）维持一段时间内的领导权，使用 Paxos 复制必要状态，并处理故障后的主节点变更。

一个典型收益是：写请求由主节点串行协调，客户端不必理解每个 Acceptor 的内部状态。代价是主节点可能成为吞吐和处理延迟的瓶颈。

但“所有读请求都送往主节点”也不是线性一致性读的充分条件。若旧主节点因网络分区没有及时得知领导权丧失，或者租约与时钟假设处理不正确，它也可能回答过期数据。可靠的线性化读取仍需要验证当前领导权，或采用适当的读屏障、读租约证明等机制。

Raft：把复制状态机落实为选举、日志和成员变更

Raft 的目标是让多个副本以相同顺序执行相同命令。相较于只描述如何选择一个值，Raft 明确规定节点角色、任期、日志匹配、提交、安全选主和配置变更等结构，因此更容易以较少的状态分支实现和验证。

领导者、候选人和跟随者如何转换

Raft 节点具有三种主要角色：Follower、Candidate 和 Leader。刚启动时通常作为 Follower，等待领导者的心跳；如果选举超时仍没有收到有效领导者消息，就转为 Candidate。

stateDiagram-v2
    [*] --> Follower
    Follower --> Candidate: 选举超时，任期加一并投自己
    Candidate --> Leader: 获得本任期多数票
    Candidate --> Follower: 发现更高任期或有效领导者
    Candidate --> Candidate: 选票分裂，超时重选
    Leader --> Follower: 发现更高任期
    Leader --> Leader: 发送心跳并复制日志

节点使用单调增加的 currentTerm 标识任期，通常持久化任期与该任期投给谁。在一次任期里，每个投票者最多投一票；任期 T 的候选人赢得多数票后，才可以成为任期 T 的 Leader。

Candidate 发送的 RequestVote 不仅携带 term 和 candidateId，还携带 lastLogIndex、lastLogTerm。接收者只有在候选人的日志至少和自己一样新、且符合任期与投票规则时才会批准。

日志新旧的比较顺序是先比较最后一条日志的任期；任期更大的更“新”，只有任期相同时才比较最后日志索引。不能简单认为“日志条数最多的节点一定当选”。

随机化选举超时降低多个节点同时参选导致选票分裂的概率。经典论文常以 150～300ms 的超时区间举例，这只是演示或特定设置，并非所有 Raft 软件的通用默认值。生产环境应该结合节点 RTT、磁盘抖动、GC 暂停和网络条件决定超时预算。

任期和多数派保证同一任期内最多一个合法 Leader。网络分区时，旧 Leader 可能尚不知道自己已经过时，因此应用层必须防止旧领导者在未重新确认权威的情况下执行不可逆外部副作用。这也是 Fencing Token、租约校验和请求重定向等机制具有工程意义的原因。

这个过程有几个容易混淆的层次：

  • Appended：日志存在于本地，不代表已获得多数派确认。
  • Replicated：某条日志已复制到一个或多个副本，还要检查是否满足提交规则。
  • Committed：协议确定该日志不会被之后的合法领导者改写。
  • Applied：已提交命令被状态机执行，业务状态真正改变。

在基本 Raft 提交规则中，Leader 不能仅凭旧任期日志条目当前位于多数派，就任意将其判定为已提交；它通过多数派复制本任期日志项推进 commitIndex，同时让之前的日志作为前缀间接提交。这一细节是保持 Leader Completeness 等安全性质的重要部分。

Follower 不需要为“每次 Apply”单独执行一套投票。Leader 的 AppendEntries 和心跳会携带 leaderCommit；Follower 在确认日志已存在后推进自己的提交位置，再按序执行状态机。

Leader 宕机后，已经返回成功的写入会怎样

假设一个写入已复制到三节点集群中的两个节点，旧 Leader 提交并返回成功，随即宕机。之后能获得多数票的新 Leader 必须具有此前已提交的日志，因此这个写入不会因为重新选举而消失。它可能仍需要通过新任期日志提交规则、心跳或后续复制，使集群的提交位置和应用位置继续推进。

相反，客户端请求超时或收到了错误，不意味着这次写入绝对没有生效。可能是在 Leader 已经复制成功之后、成功响应到达客户端之前发生了断连。客户端需要根据请求 ID、幂等语义或结果查询来处理这种不确定状态。

例如 SET X = 2 在相同初始条件下重复执行通常比 INCR X 更易重试，但不能把所有业务操作都假定为天然幂等。对于资金转移等请求，应由业务层维护请求号与去重结果，而不能仅依赖 Raft 日志避免重复业务提交。

成员变更：多数派不能在两个配置之间断开

节点扩容不是简单地更新一份服务器地址列表。考虑从 [A,B,C] 一步切换到 [A,B,C,D,E]：旧配置中的 {A,B} 是多数派，而新配置中的 {C,D,E} 也是多数派。这两个集合没有交集，如果旧、新配置在不同节点上分别生效，就可能发生各自选主的风险。

Raft 经典论文使用 Joint Consensus（联合共识），引入同时约束新旧配置的过渡阶段，使配置切换期间不能形成彼此独立的有效多数派。Raft 后续研究及一些实现也采用受严格约束的单服务器变更：每次只增加或移除一个投票节点，完成一次成员配置变更后再进行下一次。

读取与快照：写入共识并没有自动解决所有工程问题

Raft 复制日志可以让提交写入保持一致，但并不意味着任何节点的本地读都天然是线性一致读。Follower 可能尚未应用最新日志；旧 Leader 也可能在分区期间错误地认为自己仍有领导权。

需要线性一致读时，常见方案包括在 Leader 上使用 ReadIndex/读屏障确认领导权，以及符合明确时钟与租约假设的 Lease Read；普通 Follower Read 更适合能接受短暂滞后的业务。具体可选能力取决于 etcd、Consul 或其他 Raft 实现。

随着日志持续增长，系统还需使用快照（Snapshot）与日志压缩，帮助落后的节点恢复并控制存储成本。快照必须与日志索引、任期、应用进度和恢复流程一致，不能直接删除尚未安全持久化的历史记录。

ZAB 是面向主备复制的原子广播协议

ZAB（ZooKeeper Atomic Broadcast）围绕 Leader 组织写入：客户端可以连接任意服务器，但写请求最终由 Leader 排序并生成事务 Proposal，再将事务传播给参与复制的 Follower。得到满足协议要求的 Quorum 确认后，Leader 可以提交事务，并将提交决定传播出去。

ZAB 关注两个容易被忽视的性质：

  • 顺序性：各正常副本交付并执行事务的顺序相同，不能先提交依赖后置条件的事务。
  • 前缀一致性：当新 Leader 恢复历史时，应保留安全的已提交前缀，防止先前已经提交的操作在故障切换后消失或乱序。

]

例如 <1,1>、<1,2> 分别表示任期 1 内的第一、第二个事务。Leader 在任期内递增事务计数；合法的新领导任期使用更大的 Epoch，确保事务标识符不会与旧任期发生冲突。

单靠递增的 ID 还不够，协议必须约束提案的传输、确认和交付顺序。可靠有序的 TCP 连接可以保证同一连接上的字节流有序到达，但不能独自解决 Leader 崩溃、重新建连、不同 Follower 进度不一等情况。因此，还需要 ZAB 的提案排序、提交约束与领导者恢复协议。

不能将“用了 TCP”理解为“天然达成了分布式共识”。

Leader 切换时，必须恢复的是一段历史

如果旧 Leader 已经广播了多个 Proposal，却在某些事务得到足够确认之前宕机，新 Leader 不能简单地以自己当前最大的事务编号继续写入。它必须确定安全的历史前缀，恢复或清理相关未决状态，让参与者同步到一致的起点，随后才能进入正常广播阶段。

从工程角度看，ZAB 的生命周期可以概括为：

flowchart LR
    E[选举 Leader] --> D[发现与确认当前历史]
    D --> S[同步副本历史]
    S --> B[广播新事务]
    B -->|Leader 故障| E

这正是 ZAB 与“对每个槽位单独跑一次 Basic Paxos”相比的重要设计关注点。需要注意：不能据此说所有 Multi-Paxos 实现都不保证日志顺序。 实际可用的 Multi-Paxos 复制状态机实现同样可以维护日志槽位、顺序应用和领导变更安全性；ZAB 是为 ZooKeeper 的主备原子广播需求专门设计的协议。

ZooKeeper 读请求为何可能读到旧数据

为了提高读取吞吐，ZooKeeper 允许 Follower 直接服务读取请求，而写入由 Leader 排序提交。于是写入已成功返回时，某个尚未追上最新事务进度的服务器仍可能暂时返回旧数据。

ZooKeeper 主要提供顺序一致的客户端视图与线性化写入，而不是默认保证任意节点任意时刻的普通读都线性一致。

PBFT：当节点可能作恶，如何提交同一批操作

Raft 和 Paxos 的多数派假设投票节点不会故意伪造或互相矛盾地回复。当集群中存在恶意节点，这个前提不成立，单纯复制 Leader 的日志就有风险。

PBFT（Practical Byzantine Fault Tolerance）将拜占庭将军问题与实际的状态机复制结合起来。它允许有一个 Primary 负责排序，也允许部分 Backup 恶意行动；只要故障数量与通信假设满足协议要求，诚实副本仍能按相同顺序执行请求。

3f+1 个副本与 2f+1 个有效确认

经典 PBFT 采用：

[
N\geq3f+1
]

其中 f 是最多可容忍的拜占庭故障副本数。以 f=1 为例，至少需要四个副本。PBFT 的准备、提交过程围绕 2f+1 规模的确认集合工作。

为什么需要较大的 Quorum？对于 N=3f+1、每组 2f+1 个成员的两个确认集合，它们至少相交 f+1 个成员。由于最多只有 f 个恶意节点，所以交集中至少有一个诚实节点不会为互相矛盾的决定背书。

这与 CFT 的多数派思想相通，却不是同一个阈值：CFT 只需防崩溃，BFT 还要应对消息伪造、分叉承诺和故意干扰。

Pre-Prepare、Prepare、Commit 三阶段

PBFT 的请求通常包含视图编号 view、请求序号 sequence 和请求摘要 digest。Primary 为客户端操作分配序号，通过三阶段协议使诚实副本不仅知道“我看到的命令是什么”，也知道“足够多其他副本接受了同一个命令”。

sequenceDiagram
    participant C as Client
    participant P as Primary
    participant B1 as Backup 1
    participant B2 as Backup 2
    participant B3 as Backup 3
    C->>P: REQUEST(operation)
    P->>B1: PRE-PREPARE(view, seq, digest)
    P->>B2: PRE-PREPARE(view, seq, digest)
    P->>B3: PRE-PREPARE(view, seq, digest)
    Note over B1,B3: 校验消息与序号，广播 PREPARE
    B1-->>B2: PREPARE
    B2-->>B1: PREPARE
    B1-->>B3: PREPARE
    B3-->>B2: PREPARE
    Note over B1,B3: 满足 Prepared 条件后<br/>广播 COMMIT
    B1-->>B2: COMMIT
    B2-->>B3: COMMIT
    B3-->>B1: COMMIT
    Note over B1,B3: 收到 2f+1 个匹配 COMMIT<br/>达到 committed-local 条件
    B1-->>C: REPLY(result)
    B2-->>C: REPLY(result)

这里应严格区分各阶段的条件：

Pre-Prepare：Primary 提出操作、视图及序号。备份节点需要检查认证、序号范围、视图和摘要，不能无条件执行。

Prepare：正常备份节点交换带有相同视图、序号和摘要的消息。原始 PBFT 的 prepared 判定要求有效 Pre-Prepare 加上 2f 条匹配的、来自不同备份副本的 Prepare 消息；它不是“随便收到两个一样的文本”就算准备成功。

Commit：达到 Prepared 后，副本广播 Commit。收到来自不同副本的 2f+1 个有效且匹配的 Commit 消息（可以计入本节点）并满足相应前提，才能形成该副本的 committed-local 状态。之后按请求序号执行操作并返回结果。

客户端通常等待 f+1 个不同副本返回相同的有效结果，以便至少有一个响应来自诚实副本。收到少于该数量、或在超时窗口内收不到足够一致响应时，客户端不能直接认定执行失败，因为也可能只是应答丢失，需要使用请求唯一标识与重试机制。

消息认证防伪造，不防恶意节点自己说谎

PBFT 可以使用数字签名、消息认证码（MAC）等认证机制，验证消息发送者及传输完整性。它们能够阻止恶意副本假冒别的节点，却不妨碍恶意副本使用自己的合法身份发送不同内容。

真正防止冲突提交的是视图、序号、摘要、确认集合交集以及视图切换时继承安全历史等协议条件。

如果 Primary 沉默、超时或恶意排序，PBFT 通过 View Change 机制选出新主节点。新主节点必须处理此前可能已准备或提交的操作，而不是任意丢弃旧请求。检查点（Checkpoint）等机制还用于限制日志保留和状态同步成本。

PBFT 的适用范围

PBFT 相比指数级消息的理论拜占庭算法更接近工程可用。它在正常路径中的广播通信通常具有 O(N²) 的消息复杂度，节点数量扩大后，网络带宽、认证开销和慢节点都会影响提交延迟。

因此它更适合成员可识别、规模相对可控、需要容忍恶意行为的复制场景，如部分联盟链和具有明确成员身份的多组织协作系统。它不依赖像比特币挖矿那样持续竞争算力，但也不意味着没有算力、存储和带宽成本。

还要区分 Safety 与 Liveness：经典 PBFT 的安全性不依赖消息一定在固定时间送达，而在合适的部分同步等条件下才保证最终可以持续推进。若网络被无限期阻断，再完善的超时选主也不能强制消息穿过分区。

PoW：开放网络怎样把投票权变成计算成本

PBFT 依赖已知身份的副本和固定的故障比例。开放公链却允许任何人接入，攻击者可以轻易创建成千上万个虚拟身份。按账号或节点数量“一人一票”会遭遇 Sybil Attack（女巫攻击）。

PoW（Proof of Work，工作量证明）提供了另一种思路：投票权不直接取决于节点身份，而取决于参与者实际投入的计算资源和由此产生的有效工作量。

工作量证明具有“难计算、易验证”的不对称性

Hash 函数会把任意长度输入映射为固定长度输出。对于安全的密码学哈希函数，想通过不断修改输入，找到一个符合特定稀有模式的哈希结果，通常只能反复尝试。

比特币实际验证的是区块头哈希与目标值

比特币的区块由区块头和区块体构成。80 字节区块头包含版本号、上一块哈希、Merkle Root、时间戳、难度目标的紧凑编码 nBits 和 Nonce 等字段。

矿工对序列化后的区块头计算双重 SHA-256：

[
h=SHA256(SHA256(blockHeader))
]

将所得结果按比特币协议定义的格式解释为整数，必须满足：

[
h\leq target
]

目标值越小，找到有效哈希的概率越低、预期计算次数越多。由于 4 字节 Nonce 空间有限，矿工还会调整时间戳、Coinbase 的附加数据及相应的 Merkle Root，以继续寻找候选区块。

flowchart TD
    TX[收集候选交易] --> MR[计算 Merkle Root]
    MR --> H[构造 80 字节区块头]
    H --> POW[双重 SHA-256]
    POW --> OK{哈希满足目标?}
    OK -->|否| N[调整 Nonce 或其他可变字段]
    N --> H
    OK -->|是| BC[广播候选区块]
    BC --> V[其他节点验证 PoW 与全部共识规则]
    V --> CH[纳入有效链并继续扩展]

PoW 是有效性检查的一部分，绝不是“哈希足够小，交易内容就无条件合法”。全节点仍需检查交易签名、余额与花费条件、区块结构、难度规则以及其他共识约束。

分叉与“51% 攻击”的准确含义

矿工几乎同时找到有效区块时，网络里可能暂时出现多条分支。比特币节点按照累计工作量最高的有效链选择主链；在相同难度区间，经常看起来像“最长链获胜”，但准确规则不是单纯比较区块数量。

攻击者若占据较大比例算力，可以尝试秘密构造另一条有效历史，再让它以更高累计工作量替换原有一部分区块。这可能导致交易重组（Reorganization）、双花或交易审查。所谓“51% 攻击”讨论的是掌握多数算力后的长期统计优势，不表示超过 51% 就能瞬间让任何攻击百分百成功，也不表示少于 51% 就绝对不可能发生短暂重组。

多数算力不等于获得其他用户的私钥。 攻击者不能凭空为别人的地址生成有效签名、任意拿走其他人未授权的资金，也不能让无效的交易规则被正常验证节点接受。

攻击成本与网络算力、能源价格、矿机供应、经济激励和持续时间有关。早期资料中的固定人民币估算只适合其当时的假设，不应当作为今天真实攻击成本的结论。

一致哈希：如何让多个共识组共同承担业务流量

即使一个 Raft 集群有很多 Follower，同一组写操作通常仍由一个 Leader 协调。增加同一共识组的副本数可以提升冗余与故障容忍能力，但不能无限提高该组的写入吞吐。

当业务已经超出一个共识组的承载能力，应该考虑把 Key 空间拆成多个分片或分区（Shard / Partition），让不同分片分别处理读写。接下来出现的问题是：客户端如何稳定地找到负责某个 Key 的分片？

普通取模为什么在扩缩容时迁移成本高

最直观的方法是：

[
shard=hash(key)\bmod N
]

N 为参与路由的节点或分片数。这个方法在分片数稳定时非常简单，但当 N 从 3 变成 4 时，几乎所有 Key 的取模结果都可能改变，旧存放位置与新路由结果之间出现大范围错配。

对于均匀哈希的示例，三节点扩展到四节点时，普通取模可能需要重定位约 75% 的 Key。一份千万 Key 的算法演示也得到类似结果。真正生产环境中的迁移量还受 Key 分布、是否按数据量加权和分片迁移策略影响。

问题不仅是多拷贝一些数据。若路由立即切换而数据尚未迁完，读取可能找不到原有 Key；如果新旧路由并存，写请求又可能落到两个不同位置。数据路由规则的变化必须与数据搬迁、读写切流和失败回滚协同处理。

一致哈希环为什么只影响局部区间

一致哈希（Consistent Hashing）将稳定的哈希空间首尾连接，形成逻辑环。以 32 位空间为例，位置范围从 0 到 2^32-1。

节点（或分片组）通过哈希映射到环上；查询 Key 时，先计算 Key 的哈希值，然后沿顺时针方向寻找第一个节点，将该节点作为路由目标。

flowchart LR
    K[Key] --> H[计算 Key 的哈希值]
    H --> R[映射到哈希环]
    R --> N[顺时针寻找第一个节点]
    N --> G[得到目标分片或共识组]
    G --> L[访问该组当前 Leader]

新加入节点 D 时，只会从其顺时针后继节点手中接管原本落在 D 前方区间内的 Key；其他区间的路由保持不变。删除节点时，也主要影响该节点负责的区间。

在均匀分布、节点负载近似相同的理想条件下，由 N 个节点增加到 N+1 个节点，一致哈希期望迁移的 Key 比例大约为：

[
\frac{1}{N+1}
]

这只是均匀环位置下的近似分析，不是每次扩容都精确等于该比例。不同哈希函数、节点位置和虚拟节点数会造成偏差。

一组千万 Key 的演示结果可以帮助体会差距：

扩容规模 普通取模重定位比例 一致哈希示例比例
3 节点 → 4 节点 约 75.00% 约 24.30%
10 节点 → 11 节点 约 90.91% 约 6.48%

这些数字属于特定程序、节点映射和测试样本的结果，不能作为所有实现的性能承诺。

虚拟节点降低负载不均

如果环上只有三个物理节点，它们的哈希位置可能碰巧集中在一个区域，导致有的节点管理大块哈希空间，有的只管理很小一块。虚拟节点（Virtual Node）通过为一个物理节点生成多个独立位置，让环区间分配更加平滑。

例如物理节点 A 可以在逻辑环中拥有 A-01、A-02、A-03 等虚拟节点，它们最终都映射回 A。配置更多虚拟节点通常能改善数据分布，也能通过权重分配支持异构硬件。

但虚拟节点并不是自动负载均衡器：

  • 它主要改善 Key 空间分布，不能解决单个超级热点 Key 的所有请求都落在同一位置的问题。
  • 环位置变化仍然需要数据迁移；使用一致哈希只减少迁移范围，不会替我们复制数据。
  • 不同服务器容量、磁盘性能和机房故障域可能需要加权虚拟节点与副本放置策略。

对 Raft 分片做两级路由

将“一致哈希寻址节点”改为“一致哈希寻址共识组”，就能让客户端路由与组内选主相互解耦。

flowchart TB
    C[客户端] --> P[Proxy / Router]
    P --> H[一致哈希或分片元数据]
    H --> G1[Raft Group 1]
    H --> G2[Raft Group 2]
    H --> G3[Raft Group 3]
    subgraph R1[组 1 的多副本]
      A1[Leader 1]
      A2[Follower 1A]
      A3[Follower 1B]
      A1 --- A2
      A1 --- A3
    end
    subgraph R2[组 2 的多副本]
      B1[Leader 2]
      B2[Follower 2A]
      B3[Follower 2B]
      B1 --- B2
      B1 --- B3
    end
    G1 --> A1
    G2 --> B1
    G3 --> C3[另一组多副本]

组 1 的 Leader 从 A 切换到 B，只改变“组 1 → 当前 Leader”的映射，不必重新计算 Key 属于哪个分片，更不必因为单台主机宕机就把整个分片迁往别的共识组。

当实际增加或拆分共识组时，才涉及重新划分 Key 空间与搬迁数据。此时还需定义路由版本、迁移状态、源与目标双写或切流约束，并对跨组事务单独设计协调方案。

Gossip 与反熵：不要求立刻相同，怎样最终收敛

强一致性共识通过多数派决定日志，代价是在失去必要节点时，部分操作必须停止。如果业务愿意接受短时间的数据分歧，就可以通过传播、比较和修复来逐步实现最终一致性。

Gossip 是一类模仿流行病传播的分布式信息交换方式。节点不必每次都广播给全体成员，而是定期选取若干同伴交换信息，让更新随着传播轮次覆盖更大范围。

Direct Mail、Anti-Entropy 与 Rumor Mongering

三种常见传播与修复思路，针对的问题略有不同：

Direct Mail（直接邮寄）：数据发生更新时，主动向其他副本发送变化。失败时可以缓存并重试。它响应快、实现直接，但如果重试队列耗尽、数据被错误丢弃，单独依靠这种方式无法保证最终修复。

Anti-Entropy（反熵）：节点定期选择其他节点比较副本状态，发现差异后修复。即使某一次主动传播丢失，只要数据仍有可靠来源、修复能够持续执行，副本仍有机会逐渐收敛。

Rumor Mongering（谣言传播）：节点得知新消息后成为传播者，向随机选中的其他节点继续扩散消息，直到消息传播到足够多成员或满足停止条件。这种方式适合较大规模和动态成员环境中的状态通知。

flowchart LR
  A[节点 A<br/>产生新状态] --> B[节点 B]
  A --> D[节点 D]
  B --> C[节点 C]
  B --> E[节点 E]
  D --> E
  C --> F[节点 F]
  E --> F

图中 A 不需要同时联系 B、C、D、E、F。B 和 D 在收到信息后继续传播，构成去中心化的扩散路径。传播具有随机性，不保证某条消息在精确的固定轮次到达所有节点；要真正维持最终一致，还应结合去重、状态版本和周期性修复。

反熵常见的推、拉、推拉方式

假设节点 A 保存 Bob、Alice、Jerry 三条记录，节点 D 保存 Bob、Tom、Lucy 三条。两者都缺少对方的一部分数据。

模式 数据交换方向 修复效果
Push A → D D 补齐 A 已有且自己缺失的更新
Pull A ← D A 补齐 D 已有且自己缺失的更新
Push-Pull A ↔ D 双方交换差异，尽量一起完成修复

实际存储系统不应简单地将两边记录做无条件并集。因为“某条记录不见了”可能表示它从未被同步，也可能表示它已经被合法删除。若没有版本号、删除标记（Tombstone）和冲突裁决，反熵会把已删除的数据错误地重新同步回来。

同一个 Key 被不同节点并发写入时，也必须明确定义优先级或冲突解决规则。例如：

  • 使用版本向量等元信息识别因果先后与并发版本；
  • 允许并发版本共存，再由业务规则合并；
  • 采用 Last-Write-Wins 时明确时钟偏差及覆盖丢失更新的风险；
  • 适合可交换、可合并数据类型的场景，可以考虑相应的合并模型。

“所有副本最终都含有相同 Key 集合”并不足以说明“所有副本最终得到正确的业务结果”。

大分片不能每次都全量互相比较

如果每轮反熵都遍历所有记录，把全量数据传给另一个节点，网络和磁盘成本会随数据规模快速增长。工程实践通常将对比范围缩小到分片或分片组，先比较校验和、哈希摘要，必要时再深入比较具体数据块。

可以借助 Merkle Tree 等分层哈希结构逐层定位差异，或先比较变更日志、版本信息，再传输最少的补偿数据。

分片副本的典型修复场景有两种：

  1. 缺少整个分片：按照分片分配元数据确认目标节点，再从健康副本传输快照或完整分片。
  2. 分片存在但内容不一致：扫描版本或摘要，识别缺失和冲突记录，按规则修复差异并验证结果。

对于固定的少量分片副本，还可以采用确定顺序的闭环修复，而不完全依赖随机抽样。例如按照 A → B → C → A 同步差异，并在需要时继续对 B 补齐最后一轮新获得的数据，使同一分片组在一轮受控任务中尽可能收敛。

flowchart LR
  A[副本 A] -->|交换差异| B[副本 B]
  B -->|交换差异| C[副本 C]
  C -->|交换差异| A
  A -.->|必要时继续补齐| B

周期性反熵应该支持限速、暂停、超时和重试，避免在系统已经过载时又产生大量磁盘扫描和跨机房传输。

Gossip 更适合传播成员状态或更新消息，而 Raft/ZAB 的正式成员变更仍需经过各自的共识协议。不能因为 Gossip 告诉大家“新节点已经在线”，就擅自把它算入某个 Raft 组的投票多数派。

Quorum NWR：用读写副本数量调整一致性与延迟

Gossip 解决的是数据如何传播与收敛，而 Quorum NWR 关注的是：客户端究竟需要等待多少个副本才能认为读写操作完成。

其中：

  • N：一份数据的副本数量（Replication Factor），不是整个数据库的服务器总数；
  • W：一次写入成功所需的副本确认数量；
  • R：一次读取需获取多少个副本响应，用于判断应返回的版本。

W+R>N 为什么能读到已经确认的写入

假设一个 Key 有三个副本 A、B、C，即 N=3。客户端写入 X=2，要求 W=2，写入在 A、B 成功后返回。之后另一个客户端要求读取 R=2 个副本。

即使读取选中了尚未更新的 C，另一个读取对象也必须来自 A 或 B，因为三个副本中任选两个，不可能完全避开此前成功写入的两个副本。因此有：

[
W+R>N
]

这个条件保证固定副本集合中的成功写集合和读集合至少有一个交集。只要读协议能识别已确认的较新版本，就能够发现那次写入。

flowchart TB
  W[写入 X=2] --> A[副本 A：新版本]
  W --> B[副本 B：新版本]
  C[副本 C：旧版本]
  R[读取 R=2] --> B
  R --> C
  B --> V[比较版本并返回符合规则的结果]
  C --> V

这就是 Quorum 的交集原理。但有交集不等于自动获得线性一致性，这一点特别重要。

如果有多个客户端并发写入，读期间又有新的写操作，或者使用了 Sloppy Quorum、故障代写节点、异步提交与不可靠版本比较，W+R>N 本身并不能替我们处理这些场景。要保证真正的线性一致性，还需要合适的写入序列化、版本规则、读协议与成员集合约束。

它是设计较强读写可见性的重要工具，而不是“只要设置两个整数就拥有完整共识协议”。

几种配置的性能取舍

以 N=3 为例：

写确认 W 读确认 R 交集条件 主要取舍
1 1 不满足 读写延迟较低，可能读到旧副本
2 2 满足 常见平衡方案，要求读写各获得两个响应
3 1 满足 写入等待所有副本，正常读只需一个响应
1 3 满足 写入等待少，读取必须联系全部副本
3 3 满足 对单次读写请求的副本可用性要求最高

W=N 往往有利于简单的单副本快速读，但任何一个目标副本不可用都可能使写操作难以满足要求。R=N 可以减少写入端等待，但读取最容易被慢副本拖累。

若 W+R≤N，并不是所有读都会得到旧数据，而是无法仅凭读写集合大小排除读到旧数据的可能性。

副本越多并不意味着业务延迟一定越低。N 决定存储冗余和故障域选择，W/R 决定特定操作必须等待的节点数量。设计时还需注意：N 个副本如果集中在同一故障域，机架断电就可能同时失效，并不能提供预期的可用性。

Quorum 与最终一致性可以同时存在

Quorum 控制的是一次读写需要多少副本响应。Anti-Entropy、Read Repair、Hinted Handoff 解决的是没有参与本次写入的副本未来如何补齐。两者不是互斥关系，而是分别处理请求路径和后台收敛路径。

例如写入采用 W=2/N=3，第三个副本宕机导致没有获得该次更新。系统可以在不阻塞已成功写入的前提下记录补发任务，之后再通过重试或反熵使第三个副本追上。

为了避免损失与错误合并，还必须明确：写入成功后保存了多少持久副本、重试消息是否有幂等标识、并发版本如何比较、删除如何传播、恢复后如何补齐缺口。

把协议组合成一个可工作的分布式架构

在真实系统里，选一种“一致性算法”通常远远不够。要先分清数据是否属于控制平面、是否需要多个资源原子提交、是否存在恶意参与者，然后将共识、路由、复制和修复机制组合起来。

以多分片 KV 服务为例串起完整链路

设想我们开发一个需要横向扩展的 KV 服务，Key 分布在多个 Raft Group 中。一次写操作可以沿下面的链路执行：

sequenceDiagram
    participant C as Client
    participant R as Router
    participant M as Metadata
    participant L as 分片 Leader
    participant F as 分片 Followers
    C->>R: SET key=value / requestId
    R->>M: 获取最新分片路由与组信息
    M-->>R: key 对应 Group 2
    R->>L: 转发写入请求
    L->>L: 追加日志并记录请求标识
    L->>F: AppendEntries
    F-->>L: 达到多数确认
    L->>L: 提交并 Apply
    L-->>R: 已提交的执行结果
    R-->>C: success

这里面包含四层不同的保证：

定位正确性 由 Router 与 Metadata 负责。Router 必须知道 Key 属于哪个分片；如果哈希环、分片配置刚发生改变，就要能够发现路由版本过期并重新定位。

分片内的一致性 由 Raft 负责。该组 Leader 决定日志顺序，获得符合提交条件的多数派确认后返回结果。换了 Leader，不代表 Key 所属分片改变。

数据持久与恢复 由日志、持久化存储、快照以及副本追赶承担。多数派复制是协议安全性的条件；真实断电之后是否会丢失数据还依赖日志写入磁盘、文件系统和存储设备的持久性语义。

业务幂等性 由客户端请求号或状态机去重机制负责。网络异常后的重试可能产生相同请求的第二次投递，不能只因“使用了 Raft”就认为业务操作已经实现 Exactly-Once。

若一次事务同时修改 Group 1 和 Group 2，两个组各自提供强一致复制，并不会自动把跨组写入变成一个原子事务。此时还需要额外的事务协调协议与失败恢复方案。

一致性保证应该落到 API 合同上

对开发者而言，最好不要只在架构图上写“强一致”或“高可用”，而应把语义说明到请求级别。

例如：

  • 写接口返回 success 是否表示已复制到多数副本并持久化？还是只进入本地异步队列？
  • 读接口默认访问 Leader、Follower，还是执行多个副本的 Quorum 读取？
  • 写后读是否保证看到自己的更新？跨客户端写后读是否同样保证？
  • 网络超时后，客户端如何查询事务或写入请求的最终状态？
  • 分区恢复后，是否可能发生客户端已观察到的结果回退？
  • 修改成员数量、故障转移或迁移分片期间，是否需要暂停部分读写？

API 保证越具体，业务就越容易判断什么能直接依赖，什么必须由上层补充。

故障排查：从现象定位到协议环节

共识类故障往往不是“算法失效”，而是环境中的延迟、丢包、磁盘抖动、错误配置或客户端使用方式打破了部署时的预期。排查时应该沿消息的生命周期定位失败发生在哪一段。

多数派丢失后，为什么不能继续提交

以三节点 Raft 为例，如果两台机器不可达，仅剩一台机器就无法获得新的多数派确认。此时旧 Leader 可能还存活、也能接收 HTTP/RPC 请求，但它不应继续将新日志作为已提交结果返回。

需要检查网络连通性、Raft Peer 端口、当前任期、有效 Leader、成员配置和 commitIndex。增加重试次数不会创造新的多数派；忽略共识结果而直接在少数派本地写入，会破坏复制状态机的语义。

频繁重新选主，可能不是选举超时太短这么简单

Leader 心跳受到 JVM 长时间停顿、磁盘同步、CPU 饱和、网卡拥塞或网络延迟影响时，Follower 可能误以为 Leader 失效。结果是反复增加 Term、重新选主、写请求延迟升高。

排查时应观察：

  • Leader 更替次数和 Term 增长速度；
  • 心跳 RTT、RequestVote/AppendEntries 超时及 RPC 错误类型；
  • 磁盘 fsync 等待与日志持久化队列积压；
  • 线程调度停顿、GC 暂停、CPU 抢占与网络重传；
  • Follower 的日志追赶进度以及快照安装是否频繁。

调整选举超时可能改善误判，但如果真正的问题是磁盘无法稳定写入或底层网络持续丢包，单纯拉长超时只会让真实故障时的恢复更慢。

写入已经成功，为什么读取还是旧值

先确认读请求到底落在哪里：

  • 若读的是 Raft Follower，本地 lastApplied 落后于 Leader 的 commitIndex 时，返回旧值可能符合该接口的弱一致性语义。
  • 若使用 ZooKeeper 的普通本地读，Follower 可能暂时落后于已提交写入，需区分顺序保证与实时新鲜度要求。
  • 若采用 N=3, W=1, R=1，下一次查询命中未更新副本就可能读取旧数据。
  • 若系统承诺最终一致性，则应追查 Hinted Handoff 队列、反熵任务、版本冲突和 Tombstone 传播情况。

如果业务原本要求线性一致性读，就应检查读屏障、领导权确认或 Quorum 读取的实际实现，而不是简单将所有读请求强制指向一个“看起来最新”的节点。

扩容或恢复时数据路由出错

在一致哈希扩容或分片迁移期间，读写突然找不到 Key，优先核查各 Router 是否采用相同的哈希算法、虚拟节点配置、分片成员列表和路由版本。还要确认 Key 在数据迁移完成前是否被过早切到新分片。

如果单个 Raft 组的 Leader 改变了，不应立即删除原组映射或对全局哈希环重新洗牌。先从组成员信息中定位新 Leader，确认组内日志恢复状态，再恢复该组的服务入口。

防止“修复任务”成为新的故障源

Gossip、反熵、日志追赶和分片搬迁都可能在故障恢复期产生大量后台流量。若它们与前台请求共用完全没有限额的磁盘、网络和线程资源，故障刚开始恢复时反而可能再次引起超时和重新选主。

工程上应为后台任务设置并发上限、带宽预算、失败重试退避和优先级，并持续监控修复积压与预期完成时间。正确性允许最终收敛，不等于可以无限挤占线上关键请求资源。

总结：分布式一致性是多个层次的共同约束

这套知识可以串成一条连续的技术脉络：网络分区和节点故障迫使系统明确一致性与可用性的取舍；ACID、2PC、XA、TCC 解决跨业务资源协调；Paxos、Multi-Paxos、Raft、ZAB 让非恶意故障条件下的副本就操作序列形成稳定决定；PBFT 与 PoW 将讨论推进到存在恶意参与者的环境。

而当系统规模超过单个复制组的能力，一致哈希和分片负责把请求分散到不同组；若数据不必立刻在每份副本上相同，Gossip、反熵和 Quorum NWR 则提供传播、修复与可调读写等待机制。

最重要的工程判断不是记住多少算法名称，而是先明确故障模型、业务允许的旧读窗口、提交成功的含义和恢复成本，再选择能够严格兑现这些承诺的协议组合。这样才能真正回答分布式架构设计中最关键的问题：故障发生时，哪些事情必须仍然正确，哪些事情可以暂时变慢，哪些事情允许稍后再一致。
