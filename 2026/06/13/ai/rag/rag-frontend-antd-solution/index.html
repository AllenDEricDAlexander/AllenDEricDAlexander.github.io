基于 React + Ant Design 的 RAG 前端方案设计

欢迎你来读这篇博客，这篇博客主要是关于 Spring AI Alibaba + pgvector RAG 项目的前端工程方案。

上一篇后端方案已经把 Spring AI Alibaba + DashScope + pgvector + QuestionAnswerAdvisor / RetrievalAugmentationAdvisor 的后端能力设计清楚了。本文只聚焦前端：如何用 React + TypeScript + Vite + Ant Design 做一个真正能落地的 RAG 管理台和知识库问答界面。

序言

你前面贴的语雀内容，本质上完成的是后端 RAG 的最小闭环：

  1. 文档内容进入系统。
  2. 文档被切片、向量化。
  3. 向量存入 Milvus / pgvector。
  4. 用户提问时，系统进行相似度检索。
  5. 检索结果通过 QuestionAnswerAdvisor 拼入上下文。
  6. 大模型基于知识库内容生成回答。

后端做到这里，只能说明“大脑能想”。但是没有前端，用户只能拿 Postman 调接口，体验就像开法拉利还得推着走，多少有点抽象。

所以前端需要补齐四类能力：

  • 智能问答工作台：支持流式回答、会话历史、来源引用、停止生成、重新生成。
  • 知识库管理台：支持知识库创建、文档上传、文档解析状态、切片预览、重建索引。
  • 检索调试台：支持输入问题，查看召回片段、分数、metadata、TopK、阈值效果。
  • 系统配置台：支持模型参数、检索参数、文档切片参数、权限过滤参数的可视化配置。

本文会直接给出前端约束、页面设计、接口约束、TypeScript 类型、核心代码骨架和联调规范。

正文

1. 前端建设目标

1.1 目标定位

本项目不是普通后台 CRUD，而是一个 RAG 知识库问答系统前端。

它需要同时面向两类用户：

用户角色 主要诉求 典型页面
普通使用者 基于知识库提问，拿到可信回答 智能问答、会话历史、来源引用
管理员 / 运营人员 管理知识库、上传文档、查看入库状态、调试召回效果 知识库管理、文档管理、入库任务、检索调试、系统配置

因此前端不是简单做一个聊天框，而是要把 问答体验 + 知识库治理 + 检索可观测性 放到一起。

1.2 核心原则

原则 说明
先可用，再好看 第一版优先保证上传、入库、检索、问答闭环完整
问答必须可追溯 每条回答必须能展示引用来源，不能只给一段模型生成文本
参数必须可调试 TopK、阈值、知识库范围、是否重排等参数要能在调试台调整
错误必须可定位 前后端统一 traceId，接口异常要能回溯后端日志
权限不能靠前端 前端只做展示和按钮控制，真实权限过滤必须由后端执行
API Key 永不进前端 DashScope / OpenAI / 任何模型 Key 都只能留在后端或配置中心

2. 推荐技术栈

2.1 基础技术栈

模块 推荐选型 说明
构建工具 Vite 启动快，适合 React + TS 项目
前端框架 React 18+ 与 Ant Design / Ant Design X 生态匹配
语言 TypeScript DTO、API、组件 Props 都强类型约束
UI 组件库 Ant Design 后台管理台主组件库
AI 交互组件 Ant Design X，可选但推荐 用于聊天气泡、输入框、会话列表、来源展示

时间处理 dayjs 时间格式化
Markdown 渲染 @ant-design/x-markdown 或 react-markdown 渲染模型回答
代码高亮 @ant-design/x CodeHighlighter 或 shiki / highlight.js 渲染代码块
图标 @ant-design/icons 与 AntD 风格统一

2.2 Ant Design 版本建议

新项目建议：

如果要做更像 ChatGPT / 通义千问 / Kimi 这种 AI 聊天界面，建议额外加：

说明：

  • antd 负责后台管理台：布局、表单、表格、上传、弹窗、抽屉、提示、标签等。
  • @ant-design/x 负责 AI 对话场景：Bubble、Sender、Conversations、Attachments、Sources、ThoughtChain 等。

我的建议很直接：RAG 问答页用 Ant Design X，知识库后台页用 Ant Design。 这俩分工刚好，别强行用锤子拧螺丝。

4. 推荐项目结构

4.1 目录结构

4.2 分包原则

目录 约束
pages 只放页面和页面私有组件，不放通用工具
shared/api 统一请求封装，禁止页面里直接写 fetch('/api/xxx')
shared/components 业务无关或弱业务通用组件
store 只放客户端 UI 状态，不放接口缓存数据
app/router.tsx 所有路由集中维护
app/theme.ts AntD 主题 token 统一维护
pages/**/api.ts 每个业务模块自己的接口函数

一个简单标准：页面负责组装，组件负责展示，Hook 负责状态，API 文件负责请求。 不要让一个 ChatPage.tsx 写 800 行，React 也会emo。

5. Ant Design 组件使用约束

5.1 基础后台组件约束

场景 组件 使用约束
整体布局 Layout、Menu、Breadcrumb 所有页面统一走 BasicLayout，不要页面各自造布局
页面容器 Card、Typography、Space 每页顶部统一标题、描述、操作按钮
表单 Form、Input、Select、InputNumber、Slider、Switch 所有必填项必须加 rules；参数要有范围限制
表格 Table 必须设置 rowKey；远程分页统一 PageResult
上传 Upload.Dragger 统一 customRequest，统一文件类型、大小校验
状态展示 Tag、Badge、Progress、Steps 文档解析、入库任务要有明确状态
详情展示 Descriptions、Tabs、Collapse 文档详情页、切片预览页使用
反馈 message、notification、Modal、Drawer、Popconfirm 删除、重建索引等危险操作必须二次确认
加载态 Spin、Skeleton、Empty 所有异步页面必须有 loading/empty/error 状态

5.2 AI 对话组件约束

如果使用 @ant-design/x，建议这样分工：

场景 组件 说明
消息气泡 Bubble / Bubble.List 展示用户问题、AI 回答、流式回答
输入框 Sender 支持发送、停止、加载态、粘贴文件
会话列表 Conversations 左侧历史会话列表
附件 Attachments 后续支持“带文件提问”时使用
来源引用 Sources 展示 RAG 召回来源
思考过程 ThoughtChain 可选，用于展示“检索中、生成中”等步骤，不展示模型隐私推理

5.3 UI 风格约束

项目 约束
主题 使用 ConfigProvider 统一配置，禁止页面内随意写颜色
间距 优先使用 Space、Flex、Card 内置间距
图标 使用 @ant-design/icons，不要混入多套图标库
表格操作列 操作按钮顺序固定：详情、调试、重建、删除
危险操作 删除、重建、清空向量必须使用 Popconfirm
响应式 管理台最小宽度建议 1200px；聊天页兼容 768px 以上
错误提示 统一展示 message + 可复制 traceId
空状态 不要空白页面，使用 Empty 给出下一步操作
Markdown 模型回答必须做 XSS 防护，不能直接 dangerouslySetInnerHTML

6.5 检索调试页

6.5.1 页面目标

检索调试页是 RAG 系统非常关键的“验货台”。它不调用大模型，只看检索效果。

支持：

  • 输入 Query。
  • 选择知识库。
  • 设置 TopK。
  • 设置相似度阈值。
  • 设置 metadata filter。
  • 查看召回 chunk。
  • 查看 score。
  • 对比纯向量检索、关键词检索、混合检索。

6.5.2 页面布局

收到 retrieval 更新来源列表和检索状态
收到 delta 追加到当前 AI 消息 content
收到 done 结束 loading，保存 usage
收到 error 停止 loading，展示错误消息
点击停止 调用 AbortController.abort()
页面离开 自动中断当前流

30. 前后端联调规范

30.1 联调顺序

建议按这个顺序联调：

flowchart TD
    A[知识库列表接口] --> B[创建知识库]
    B --> C[文档上传]
    C --> D[入库任务状态]
    D --> E[文档列表]
    E --> F[chunk 列表]
    F --> G[检索调试]
    G --> H[非流式问答]
    H --> I[流式问答]
    I --> J[来源引用展示]

不要一上来就联调流式问答。先把知识库、文档、chunk、检索调试打通，最后再接 Chat。这样问题更容易定位。

30.2 Mock 策略

前端开发初期可以用 Mock：

  • 知识库列表 Mock。
  • 文档列表 Mock。
  • 入库任务 Mock。
  • 检索结果 Mock。
  • SSE 流式 Mock。

但 Mock 数据必须遵守同一套 TypeScript DTO。不要 Mock 一套、后端一套，最后联调现场大型对线。

30.3 接口文档约束

后端需要给前端提供：

  • OpenAPI 文档，或 Markdown 接口文档。
  • 每个接口的请求/响应示例。
  • 错误码表。
  • SSE event 类型说明。
  • 文件上传大小和类型限制。
  • 认证方式说明。

启示录

RAG 前端最容易被低估。很多人觉得“前端不就是一个输入框吗”，但真正上线后你会发现，用户最关心的是：

  • 你回答的依据是什么？
  • 为什么这条文档被召回？
  • 能不能看到原文？
  • 文档为什么还没入库？
  • 为什么这次回答和上次不一样？
  • 出错了后端能不能定位？

所以，一个靠谱的 RAG 前端，不只是聊天框，而是 知识库治理 + 检索可观测 + 可信回答体验 的组合。
